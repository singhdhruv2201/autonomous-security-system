# Activity recovery, processing and visibility — phases 5–6

The CRM activity environment now covers capture, signed delivery, recovery,
durable processing and a dashboard Activity view. This extends the
[phase 2–4 delivery guide](activity-delivery.md). Activity policies, secret scanners,
AI investigation and remediation remain disabled; the existing snapshot-based
inactive-owner rule continues independently.

## Start or upgrade the local environment

Back up CRM and inbox volumes before upgrading. `make setup` adds the dedicated
`CRM_RECOVERY_TOKEN` without rotating any existing credential. CRM startup registers
a read-only Activity Reader with `events:read` on `crm-activity`; existing grants
and revocations are preserved. Its resource is included in the graph inventory.
CRM schema remains v4; the inbox gains additive checkpoint and normalization tables.

```sh
make setup
CRM_ACTIVITY_ENABLED=1 CRM_WEBHOOK_ENABLED=1 \
AWASI_ACTIVITY_WORKER_ENABLED=1 AWASI_ACTIVITY_URL=http://awasi-ingest:8003 \
docker compose --profile activity up --build -d --wait crm awasi-ingest security-api dashboard
```

Open [the Activity view](http://localhost:3000/#activity). Save these four settings
in the ignored local `.env` if subsequent `docker compose up` commands should retain
enablement. Without them capture/delivery/processing default off and the security
API reports activity disabled. `CRM_RECOVERY_TOKEN` is required by the updated
Compose configuration; run `make setup` before deploying it. Nothing in the source
change resets or automatically redeploys a running demo.

The receiver and processing worker run in `awasi-ingest`, using the persistent
`activity-inbox` volume. The worker calls CRM at the fixed `CRM_URL`; it never needs
Neo4j, models or CRM administrator credentials. The security API proxies authenticated
activity reads to `AWASI_ACTIVITY_URL`. The dashboard uses its existing server-side
viewer credential. The browser receives no CRM, webhook or security API secrets.

The local receiver requires both `SECURITY_VIEWER_TOKEN` and
`SECURITY_OPERATOR_TOKEN` for activity reads. Webhook signing secrets do not grant
read access. In normal Compose operation these are already generated by setup and
shared with the security API. Reads remain scoped to Helio; this is not tenant
provisioning or public dashboard authentication.

## Recovery contract

Only an active `events:read` grant on the exact `crm-activity` resource can use:

| CRM endpoint | Behavior |
| --- | --- |
| `GET /activity/status` | Current source instance, high watermark, earliest retained sequence, capture state and bounded queue/capacity summary |
| `GET /activity/events` | Ascending security events after `after`, no later than `through`, maximum `limit` 200 |

Both use the dedicated recovery bearer credential. Ordinary employees, agents,
metadata observers and administrators without that scoped grant are denied. The
recovery reader cannot read customer records or ordinary CRM metadata. Successful
recovery calls are audited in the operational stream and are not exported recursively.

Fetch status first, then pass its `source_instance_id` and `high_watermark` as
`through` throughout paging. The response includes `next_after` and `has_more`.
Bounds are validated; wrong epochs return 409, expired history returns 410 and
invalid cursor ranges return 422. The high watermark uses the allocated sequence,
so deleting the entire retained history cannot disguise an expired feed as empty.

The worker polls status every five seconds even if no webhook arrives. This repairs
a missing final event as well as a missing middle event. It follows at most ten
100-event pages per poll, holding a fixed source/watermark during each pass. Network
reads have a five-second timeout, bounded bodies and no redirects or environment
proxy forwarding. Plain HTTP is limited to the local sandbox hosts; configure
HTTPS for other destinations.

Pull uses the same schema validation, company/source/epoch binding and durable
deduplication boundary as signed push. A malformed page, conflicting event, changed
source or missing sequence never advances a checkpoint past unproven evidence.
Transient failures retain receipts and retry on subsequent polls.

## What the checkpoints mean

Each company/source/instance has two durable contiguous checkpoints:

- **Received through:** every sequence up to this point is committed to the inbox.
- **Processed through:** every sequence up to this point has committed normalized
  evidence. It is not a policy assessment or remediation result.

An out-of-order event can be received and normalized while both checkpoints remain
behind an earlier gap. Processing writes normalized evidence and its checkpoint in
one SQLite transaction. A crash or failed insert leaves work pending; another worker
pass or restart retries it without creating a duplicate. The original immutable
inbox retains its legacy `status=pending` field for compatibility; current pending
work is an inbox row without its corresponding `normalized_events` row. Health
and processing queries use this relationship, not the legacy field.

Source instances are kept separately. A changed instance increments a persistent
reset counter; it never reuses the old cursor or discards old history. Identity
conflicts also leave a persistent integrity warning. These warnings deliberately
prevent an automatic claim of complete coverage and currently require investigation
and an explicit future repair/migration workflow; there is no “dismiss and mark
healthy” endpoint. Expired source history remains a gap until restored. Push can
still collect new events while that gap exists.

## Activity API and dashboard

Authenticated viewer/operator reads are available on the receiver and through the
security API:

| Endpoint | Result |
| --- | --- |
| `GET /activity` | Company-scoped requests with nested lifecycle stages, operation outcome, response status, scan state and completion |
| `GET /activity/health` | Source watermarks, receipt/processing cursors, gaps, pending work, queue snapshot/dead letters, freshness, source resets and safe failure codes |

`/activity` accepts `limit` (1–200), `before`, `snapshot`, exact `actor_id` (up to
200 characters), and `outcome=allowed|denied|failed`. It returns `next_before` and
`snapshot`; reuse both to page older requests within the same processing snapshot.
Newly normalized evidence appears on a fresh request, not unexpectedly halfway
through that snapshot. Request identity includes source instance and source, so a
reset cannot merge unrelated requests. Company comes from server authorization,
never the caller's query.

The dashboard shows one request row rather than four separate business actions.
Expand a row for request, operation, prepared response and completion evidence.
Direct store calls and interrupted requests may have fewer stages. Missing completion
is unknown; an allowed operation is not a benign-intent verdict. Scanners explicitly
show **Not run**.

Activity refreshes every five seconds while its newest page is visible. Automatic
repainting pauses while evidence is expanded, filter controls have focus or older
pages are loaded; use **Refresh activity** for a new snapshot. Graph observation
refreshes cannot discard an expanded request or draft activity filters. Actor and
outcome filters run server-side; older-page navigation uses bounded cursors.

Health is evaluated against the latest known source watermark, not unseen future
requests. A source check older than 30 seconds is stale. Receipt and processing lag
are reported in event counts; the oldest pending receipt also has an age in seconds.
Queue counts and retained capacity are sampled at the displayed source-check time.
Dead letters are visible even if recovery already obtained those events, because
the push delivery problem still needs review. New activity does not silently clear
source resets, integrity failures or expired history.

## Outage and recovery operations

If Awasi is down, CRM continues while its local audit capacity permits. The sender
retries and retains exhausted attempts. When Awasi returns, its worker resumes
pending normalization and polls CRM to repair missing receipts. After fixing a push
problem, administrators can replay dead letters through the existing
`POST /activity-deliveries/{sequence}/replay`; see the delivery guide for signing-key
rotation and replay semantics. Pull recovery does not falsify a successful push
acknowledgement or erase delivery diagnostics.

If the recovery credential is invalid or revoked, the UI reports the connector
failure. Restore the intended credential or explicitly review its grant; startup
never revives a revoked grant. If source history is expired or conflicted, preserve
both databases and investigate/restore retained evidence rather than resetting
checkpoints or deleting the inbox.

Set `AWASI_ACTIVITY_WORKER_ENABLED=0` and recreate `awasi-ingest` to stop recovery and
processing while keeping signed admission available. Clear `AWASI_ACTIVITY_URL` and
recreate the security API to disable its activity view. Use the earlier capture and
sender flags to stop those independently. Retained state survives disabling.

The 10,000-event cap per CRM stream remains. Delivered and operational events count,
including health checks and recovery traffic. No unattended retention, archival or
automatic pruning is implemented. Monitor retained capacity and keep this deployment
within a controlled local test window; production evidence lifecycle and capacity
qualification are separate phases.

## Acceptance evidence

Tests exercise real SQLite and local HTTP: scoped and revoked recovery access,
fixed-watermark paging, missing middle/final events, push/pull duplicates, source
reset and expiry, out-of-order checkpoints, processing failure/restart, invalid
pages, persistent conflicts, request grouping, filters and pagination. A real Neo4j
test verifies the new reader grant/resource without breaking snapshot observation.
Frontend tests cover escaping, honest coverage state, request grouping and preserving
activity UI state during background graph refreshes.

The 2026-10-31 Docker acceptance run used the retained local Compose volumes, after
consistent SQLite backups of CRM and inbox. All six services were healthy. An allowed
CRM read and a 401 denial made while `awasi-ingest` was stopped retained eight source
events. The browser displayed **Activity unavailable / Coverage unknown** during the
outage. After restart, both requests appeared exactly once with four stages each;
receipt and processing cursors caught up with no gaps. Denial filtering, expanding
evidence, pagination and the overview's **View activity** navigation were checked in
the browser. No credentials, grants, customer records or source identities were reset.

Run the gates with `.venv/bin/python -m pytest -q`, `make test-integration`,
`make test-ui`, and `docker compose --profile activity config --quiet` after setup.
The existing Starlette/httpx deprecation warning is unrelated to these phases.

### Reproducible receipt latency qualification

Build the current code into the running CRM and receiver before measuring. The
benchmark generates authorized reads of the six synthetic customers and reads only
timing/identity metadata through read-only SQLite probes inside the containers.
It does not export customer bodies or credentials, change grants, prune history,
or stop services. Keep other CRM traffic idle for a run: extra events, a source
reset, missing/duplicate stages, missing acknowledgements, exhausted capacity or
invalid clocks invalidate the sample instead of silently shrinking it.

```sh
docker compose up --build -d --wait
make benchmark-activity BENCHMARK_ARGS='--samples 20 --warmup 5 --concurrency 4 --output work/activity-latency-20.json'
# Larger burst; this missed the conservative target on the measured machine:
make benchmark-activity BENCHMARK_ARGS='--samples 100 --warmup 10 --concurrency 4 --output work/activity-latency-100.json'
```

There is no pacing between requests: each of four client threads starts its next
read when the previous HTTP response returns. Warmup events are fully delivered
before the measured burst. Each request returns six customers / 959 JSON bytes
and produces four separate security events, 434–672 bytes each in these runs.
The report uses nearest-rank p95 over **all** measured events, excluding warmup.
It saves hardware/runtime versions, container image identities, Git state, load,
payload sizes and min/median/p95/max timings as JSON. Defaults are 100 requests,
10 warmups and concurrency four; bounds are enforced before issuing traffic.

Two timings are deliberately separate:

- **First receipt:** source `occurred_at` to the inbox's persisted `received_at`.
  Push and recovery share the first receipt. This timestamp is sampled before the
  admission transaction commits, so it alone is not an exact durable-commit timer.
- **Durable acknowledgement bound:** source `occurred_at` to CRM's recorded
  successful webhook HTTP 200/202 acknowledgement, which follows the receiver
  commit. This is a conservative upper bound; recovery can have stored the event
  earlier. The tool declares `target_met` only when both p95 values are ≤ 2 seconds.

The CLI returns 0 for a qualified run, 1 for a complete measurement that misses
the target, and 2 for an incomplete/invalid measurement. `make` may translate a
recipe failure to exit 2. It never equates a fast CRM response with delivered
evidence. This measures receipt, not normalization, UI refresh, policy or remediation.

Measured 2026-10-31 on Apple M4 Pro / 48 GiB RAM, macOS 26.6.2 arm64,
Docker Engine 29.6.1 with a 14-vCPU / 15.6-GiB Linux VM, container Python 3.11.18,
real HTTP and persisted SQLite volumes. Capture, signed push and five-second
recovery polling were enabled. This was a shared development machine, not an
isolated production capacity test. Both source and receipt clocks ran in that VM.

| Sender | Measured requests / events | Warmups | Concurrency | Receipt median / p95 | Acknowledgement median / p95 | Conservative target |
| --- | ---: | ---: | ---: | --- | --- | --- |
| Original, pauses after every event | 20 / 80 | 5 | 4 | 3,805.94 / 3,813.07 ms | 10,361.51 / 19,426.04 ms | Missed |
| Drains ready events | 20 / 80 | 5 | 4 | 415.61 / 631.37 ms | 417.77 / 637.82 ms | Met |
| Drains ready events, larger burst | 100 / 400 | 10 | 4 | 1,761.34 / 1,896.54 ms | 2,465.57 / 3,090.10 ms | **Missed** |

The original worker slept 250 ms after every event, limiting ready-queue drainage
to roughly four events per second before network/storage costs. It now drains due
events continuously and waits 250 ms only when idle or after a storage exception;
retry schedules, bounded attempts, leases and shutdown checks remain enforced.
Regression tests cover idle/error backoff and complete concurrent HTTP lifecycles.

The two-second bound is qualified for the declared **20-request burst only**.
The larger burst's first-receipt p95 was below two seconds, but its durable
acknowledgement bound missed, so that load is not qualified. This records the
phase-6 acceptance boundary; it does not establish sustained throughput or a
production SLO. The 10,000-event cap and absent retention still limit unattended use.
Local raw reports and browser evidence are under ignored `work/phase56-20261031/`;
the method and measured results above remain available in Git.
